# Compound GTM Architecture

Compound GTM is a context-first go-to-market system. It loads what a team already knows, routes to the smallest useful move, and ends substantial work by writing evidence-graded lessons back into a small, plain-text GTM home.

## Design principles

1. **Memory before generation.** Load the home before drafting anything. Output quality is capped by what the system knows about the buyer.
2. **Evidence is first-class.** Every durable line carries `Observed`, `Heard`, `Reported` or `Believed`. Promotion from belief to rule needs evidence, not repetition.
3. **Outcome routing.** Start from what the person is trying to get done, not a mandatory stage sequence.
4. **Human ownership.** ICP, positioning, offer and price are the team's decisions. Moves propose, show evidence and push; they don't silently replace.
5. **Live systems need approval.** Sending, publishing, spending and CRM writes require explicit, action-specific approval.
6. **Permission-aware proof.** Proof is tagged `public`, `anonymised` or `internal`; unknown means internal. One client's data never enters another client's home.
7. **Progressive disclosure.** The front door is one `SKILL.md`. Each move is a separate reference file, loaded only when used.
8. **One source, several surfaces.** `skills/compound-gtm/` is canonical. Claude Code commands and the claude.ai zip are generated from it.

## Layers

### Context layer

`references/context-contract.md` defines the home layout, what belongs in each file, load order, behaviour when the home is missing or thin, and write safety. `references/evidence.md` defines evidence levels, permission tags, play statuses and rules for honest numbers. Every move reads both.

### Orchestration layer

`SKILL.md` is the front door. It finds the starting point (material in hand, an existing home, or nothing), routes by outcome, and names common compositions. It never forces setup when there is work to do now. It also defines the **Review** route — lenses chosen by asset type, merged into one verdict, one fix list and a fixed version — and scales every move to the size of its input.

### Move layer

24 moves in `references/moves/`, grouped as home, market, message, motion, pressure-test and learn. Each file follows the same shape: purpose, when to use, what it reads, steps, output, what could compound.

The pressure-test moves (`buyer`, `cfo`, `rival`, `inbox`, `committee`) are lenses: they diagnose and do not rewrite. Drafting moves (`sequence`, `asset`) fix.

## The home contract

```
gtm-home/
├── README.md  ICP.md  POSITIONING.md  PROOF.md  PLAYS.md  VOICE.md  COMPANY.md
├── motions/<yyyy-mm>-<slug>/{BRIEF,RESULTS,RETRO}.md + assets/
├── accounts/   (optional)
└── field/      (optional — raw notes waiting to be mined)
```

- Created only once its destination is explicit or safely resolved. `scripts/create_home.py` never overwrites.
- Existing workspaces keep their structure. Compound GTM maps onto them rather than imposing its own.
- Missing or sparse files never block work.

## The compounding contract

Compounding means updating a maintained file, not claiming memory.

| Learning | Destination |
|---|---|
| Who buys, triggers, committee, disqualifiers | `ICP.md` |
| Alternatives, why we win or lose, objections, message | `POSITIONING.md` |
| Claim + backing | `PROOF.md` |
| A motion's status, results and rules | `PLAYS.md` |
| Tone, words, formatting | `VOICE.md` |
| Offer, price, terms, capacity | `COMPANY.md` |
| One-off context | The motion's `RETRO.md` |

Rules:

- Lessons are atomic, dated and sourced. Mixed lessons are split, not duplicated.
- Inferred lessons are proposed and confirmed before writing. `Believed` lessons are stored only as open hypotheses.
- Conflicts with existing lines are surfaced, never overwritten.
- Lessons never go into the skill's own files or an installed plugin copy.

## Packaging

- `skills/compound-gtm/` — canonical. Frontmatter uses only `name` and `description` for cross-runtime compatibility.
- `commands/` — generated by `scripts/build.py`, one `/cg-<move>` per move plus `/cg-desk`.
- `dist/compound-gtm.zip` — generated; the claude.ai upload. Built with fixed timestamps, so an unchanged skill rebuilds to an identical archive.
- `.claude-plugin/` — plugin and marketplace manifests.
- `assets/` — README visuals, generated by `scripts/render_assets.py` from the brand palette and the example home's own numbers.
- `.github/workflows/build.yml` — runs `python scripts/build.py --check` and a `create_home.py` smoke test on every push.

## Readiness tests

A change is ready when the first four pass in `python scripts/build.py --check` (CI runs it) and the last three hold on review:

1. `SKILL.md` frontmatter holds only `name` (matches the folder) and `description` (≤ 1024 characters), and every move file starts with `# <move> — <purpose>`.
2. Every move named in `SKILL.md`'s routing table has a file, every move file is routed, and every "N moves" in the docs matches the count.
3. Plugin manifest, marketplace manifest and the top `CHANGELOG.md` entry share the same version.
4. Relative links resolve, and `commands/` and `dist/` match the skill.
5. No move creates files before resolving a destination, or sends, publishes or writes to a live system without approval.
6. No move presents a `Believed` claim as fact in customer-facing output.
7. The example home contains only invented companies, people and numbers, and says so.
